# iOS 75 Native Incoming Audio Calls

- [ ] **Part 1 — replace the registration collision with a single telecom owner.** Base all work on `52688e6` and retain outgoing-call behavior unchanged. Build a local fork/extension of `expo-callkit-telecom` v1.0.1 that owns exactly one runtime `PKPushRegistry` and one runtime `CXProvider`; incoming Android-to-iPhone audio uses that registration and its canonical `CallSession`. Remove `OLCallManager` ownership of a second registry/provider without changing outgoing calls, video, rooms/LiveKit, Android, or non-call server endpoints. Dedupe by server `callId` and canonical CallKit UUID; PushKit/page ingress races must create and report exactly one incoming call.

- [ ] **Part 1 — make incoming reporting and CallKit actions reliable.** Configure the provider before reporting, set the ringtone in `CXProviderConfiguration`, retain `audio` and `voip` background modes, pre-create objects before unlock, report in the PushKit same-run-loop window, and use `endAllCalls` for terminal cleanup. Add reporting backoff, a loud 2-second watchdog, and a visible in-app fallback. That fallback and every system/in-app answer must request and fulfill the same `CXAnswerCallAction`. Log every `CXProvider` callback with UUID, milliseconds since signaling, and a redacted session snapshot to `[OLCalls]` and client-diag. Keep b74’s audio reset before every ring and every call end. Do not retain manual incoming-call AVAudioSession activation or WebKit audio in the incoming call path.

- [ ] **Part 2 — create the native Swift mediasoup lane without JavaScript media control.** Evaluate the specified existing wrappers first, fork the selected VLprojects source baseline, and do not use its prebuilt m140 WebRTC binary. Compile the libmediasoupclient wrapper only against a source-proven Stream WebRTC m125 build that is ABI-compatible with `StreamWebRTC` `125.6422.070` used by React Native package `125.4.5`. Native code must own raw WSS signaling, Device load, send/recv transports, Opus 48 kHz producer and consumer, `CXAnswerCallAction` outcome, and `didActivate` media start. JS receives UI events asynchronously only.

- [ ] **Part 2 — meet the call-performance and audio rules.** `CXProvider` is the sole authority. Turn audio on only in `didActivate`; no manual AVAudioSession activation for incoming calls. Prewarm Device/router capabilities, liveness-validated transport reservation, cached early ICE, and precomputed DTLS data without synchronous disk/network on answer. Preserve mediasoup UDP first, then Coturn UDP/3478, TCP/3478, TURNS/443; use a non-blocking trickle-equivalent mechanism against ICE-lite and log it. Keep Opus 48 kHz SFU pass-through and disable/manage interruptions only with a verified m125 API. Target under 500 ms from answer to audio on a good connection.

- [ ] **Server payload boundary only if necessary.** Do not change server routing, media order, Android behavior, or non-call endpoints. If trimming the VoIP payload, first create a backup and change only `server/calls/voip.ts` at the APNs serialization boundary. Preserve `type`, `callId`, `callerName`, `video`, `expiresAt`, and `declineToken`; do not alter the shared FCM/Android payload.

- [ ] **Validation and handoff.** Add tests for one registry/provider, dedupe across PushKit/page ingress order, no duplicate report, token cold start, watchdog/fallback action reuse, outgoing behavior, b74 reset, native Opus media configuration, raw WSS framing, and APNs payload trim when present. Produce a pass/fail table for every brief item. Do not merge to main or ship App Store/TestFlight. Device validation must include: “Keiko calls from Pixel 10 audio-only, Donny answers in-app, both hear each other immediately, native call screen visible.”
